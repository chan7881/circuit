# 물리 검증 절차 (시뮬레이터 만들 때 반드시 거칠 것)

> 2026-08-07, 직선 도선 나침반이 **180° 반대**를 가리키던 버그를 잡으면서 정리했다.
> 그 버그는 "자기장이 반지름 방향과 수직인가"만 검사하는 약한 테스트를 **통과하고 있었다.**
> 아래 절차는 그런 종류의 오류를 구조적으로 걸러내기 위한 것이다.

시뮬레이터는 학생이 **관찰해서 법칙을 스스로 찾아내는** 도구다. 그래서 화면에 보이는 것이
실제 물리와 어긋나면, 단순한 그래픽 결함이 아니라 **학생에게 틀린 법칙을 가르치는 것**이 된다.
"그럴듯해 보인다"는 검증이 아니다.

---

## 0. 언제 적용하나

물리 법칙으로 방향·부호·크기가 정해지는 것을 화면에 그릴 때 **항상**. 특히 위험한 것:

- **방향이 있는 벡터**: 자기장, 전기력, 전류, 힘, 속도
- **회전 방향(손잡이, handedness)**: 오른손 법칙, 외적이 들어가는 모든 것
- **극성**: N/S, +/−, 전자 이동 방향 vs 전류 방향
- **좌표축을 갈아타는 곳**: 2D 모델 → 3D 장면, 모델 좌표 → 화면 좌표

> 부호 하나만 뒤집혀도 결과가 정확히 반대가 되는데, 화면만 보면 "뭔가 돌고 있다"로 보여
> 알아채기 어렵다. 오늘 버그가 정확히 그랬다.

---

## 1. 이론값을 **따로** 구한다

시뮬레이터 코드를 쓰지 말고, 교과서 공식에서 직접 계산한다. 코드를 재료로 쓰면
"코드가 코드와 같다"만 확인하게 되어 아무것도 검증되지 않는다.

```js
// 예: 오른손 법칙 B ∝ Î × r̂ 을 직접 세운다
function cross(a, b) { return [a[1]*b[2]-a[2]*b[1], a[2]*b[0]-a[0]*b[2], a[0]*b[1]-a[1]*b[0]] }
const expected = norm(cross(currentDir, rHat))
```

자주 쓰는 이론 기준:

| 상황 | 이론 기준 |
|---|---|
| 직선 도선 주위 자기장 | `B ∝ Î × r̂` (오른손 법칙), 세기 ∝ 1/r |
| 코일·고리의 자기 모멘트 | 전류 순환에 오른손 감기 → 엄지가 N극 |
| 자기장 속 도선이 받는 힘 | `F ∝ I × B` |
| 전하 사이의 힘 | 같은 부호 밀림 / 다른 부호 끌림, 세기 ∝ 1/r² |
| 정전기 유도 | 가까운 쪽이 **반대** 부호, 전체 전하량은 보존(0) |
| 회로 | 전류 방향 = 전자 이동 방향의 **반대** |

## 2. 모델과 대조하고, 차이를 **수치로** 남긴다

"비슷하다"가 아니라 각도(°)나 배율로 적는다. 로그에 남겨 두면 나중에 판단 근거가 된다.

```
(130,0) 기대=[0.00,-1.00] 실제=[0.00,1.00] 차이=180.0°
```

## 3. 차이의 **성격**을 판정한다 — 버그인가, 오차인가

| 차이 | 판정 | 할 일 |
|---|---|---|
| 180°, 90° 등 **딱 떨어지는 값** | 부호·축이 뒤바뀐 **버그** | 반드시 고친다 |
| 0에 가까움(< 1°, 수치오차 수준) | 이산화·부동소수점 오차 | 통과 |
| 어중간(수°~수십°) | **근사 모델의 한계** | 그 근사가 쓰이는 자리에서 받아들일 만한지 따로 판단 |

세 번째가 가장 조심스럽다. 판단 기준은 **"그 오차가 학생이 관찰할 대상을 왜곡하는가"**다.

> 실제 사례(2026-08-07): 코일을 점 쌍극자로 근사한 식이 나침반 자리에서 실제 장과
> **25.7°** 어긋났다. 나침반만 보면 티가 안 나지만, 자기력선을 실제 모양대로 그리는 순간
> **바늘이 자기력선을 따라가지 않는** 화면이 된다. 그래서 오차로 넘기지 않고 비오-사바르
> 적분으로 교체했다. — 판단 기준은 "몇 도냐"가 아니라 **"무엇이 어긋나 보이느냐"**였다.

## 4. 테스트를 추가하되, **방향까지** 못 박는다

약한 검증은 부호 뒤집힘을 그대로 통과시킨다. 대칭성·수직성·크기만 보는 검증이 특히 그렇다.

```js
// ✗ 약함 — 시계 방향이든 반시계 방향이든 통과한다
close(dot(rHat, B), 0, '자기장은 반지름 방향과 수직이다')

// ✓ 방향까지 고정 — 손잡이가 뒤집히면 반드시 실패한다
close(dot(normalize(B), expectedFromRightHandRule), 1, '오른손 법칙 방향과 일치')
```

가능한 모든 조건 조합에서 검사한다(전류 방향 ±, 극 배치 ±, 여러 위치).

## 5. **그 테스트가 진짜인지 확인한다** (변이 검사)

새 테스트가 통과하는 것만으로는 부족하다. **일부러 버그를 되돌린 복제본**에서
그 테스트가 실패해야 비로소 검증이다.

```bash
cp -r <시뮬폴더> $SCRATCH/mut/
sed -i 's/{ x: ry, y: -rx }/{ x: -ry, y: rx }/' $SCRATCH/mut/js/model.js   # 부호 되돌리기
# 복제본 test.html 을 열어 실패하는지 확인 → 16개 실패 = 검증이 살아 있음
```

실패하지 않으면 그 테스트는 허수다. 다시 쓴다.

## 6. **렌더링까지** 확인한다

모델이 맞아도 화면에 그리는 단계에서 또 뒤집힐 수 있다. 특히 위험한 지점:

- 모델 2D `{x, y}` → 3D 장면 `{x, ?, z}` 축 매핑
- `rotation.y = -angle` 처럼 **부호가 붙은 회전**
- 카메라 위치에 따라 달라지는 화면 좌우/상하

방법: **먼저 예측을 세우고** 스크린샷과 대조한다. 스크린샷을 먼저 보고 해석하면
보고 싶은 대로 읽게 된다.

```
예측: 위에서 내려다보면 화면오른쪽=+x, 화면위쪽=−z.
      전류가 화면 밖으로 나오므로 바늘은 반시계로 돌아야 한다.
      → 오른쪽 나침반의 빨간 끝은 화면 '위'를 가리켜야 한다.
확인: 오른쪽=위, 위=왼쪽, 왼쪽=아래, 아래=오른쪽 → 반시계 ✓
```

## 7. 화면에 **그려 놓은 조건**과도 맞는지 본다

학생이 보고 법칙을 적용할 대상(전류 화살표, N/S 딱지, 전지 +/−)이 화면에 있다면,
결과가 그것과 맞아야 한다. 오늘 버그의 본질이 이것이었다 —
**"전류는 위로 흐른다"고 그려 놓고 자기장은 반대로 돌렸다.**

## 부록: 이 저장소에서 확인할 때 걸리는 함정

- **브라우저가 ES 모듈을 캐시한다.** 코드를 고쳤는데 화면이 그대로면 십중팔구 이것이다.
  `python -m http.server <새 포트>` 로 **포트를 바꿔** 새 오리진에서 열면 확실히 새로 받는다.
- **백그라운드 탭에서는 `requestAnimationFrame`이 아예 돌지 않는다**(측정: 900ms 동안 0회).
  자동화로 확인할 때는 애니메이션 루프를 기다리지 말고 `scene.update(...)` /
  `render.draw(...)` 를 **직접 호출**한 뒤 그린다.
- **WebGL 캔버스는 `preserveDrawingBuffer: true` 가 있어야** `toDataURL()`로 화면을 뜰 수 있다.
  (이 저장소의 3D 시뮬레이터는 이미 켜 두었다.)
- 스크린샷은 `canvas.toDataURL()` → 로컬 수신 서버로 POST → 파일로 읽는 방식을 쓴다.
  `mcp__claude-in-chrome__computer` 의 screenshot 은 이 환경에서 자주 시간 초과된다.
