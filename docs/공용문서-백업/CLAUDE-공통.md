# 교육 자료 제작 공통 규칙

중학교 과학 수업에 쓸 자료를 만든다. 이 폴더 아래 프로젝트에서 작업할 때 함께 읽힌다.

**만드는 사람**: 중학교 과학 교사. 실제 수업에 쓰는 물건이고, 학생이 직접 만진다.

## 문서 지도

| 층 | 파일 | 담는 것 |
|---|---|---|
| 환경 | `~/.claude/CLAUDE.md` | 이 PC·원격 제어·파일 검색·브라우저 자동화·서브에이전트 |
| **공통** | **이 파일** | 교육 자료를 만들 때 늘 지킬 것 |
| **라우팅** | **`문서편집_라우팅.md`** | **문서 파일을 고치거나 읽기 전 진입점** |
| 절차서 | `hwpx_` · `pptx_` · `xlsx_편집_절차.md` · `circuit/docs/물리_검증_절차.md` | 확장자·분야별 기술 노하우 |
| 프로젝트 | `<프로젝트>/CLAUDE.md` · `<프로젝트>/docs/` | 그 프로젝트의 구조·진행·결정 기록 |

**백업**: 환경·공통 문서와 `memory\`는 git 밖이라 **`G:\내 드라이브\Claude-설정백업\`**에 사본을
둔다. 공통 문서는 `circuit/docs/공용문서-백업/`에도 있다. **사본이 아니라 원본을 고친 뒤 갱신.**

### 새 규칙·노하우를 적을 때 — 어디에 적나 ★

| 성격 | 가는 곳 |
|---|---|
| 이 PC·도구에 관한 것 | `~/.claude/CLAUDE.md` |
| 교육 자료 전반에 통하는 **원칙** | **이 파일** |
| **특정 확장자를 다루는 기술** | 그 확장자의 **절차서** |
| 한 프로젝트에만 통하는 것 | `<프로젝트>/CLAUDE.md` |
| 결정의 **이유와 버린 대안** | `<프로젝트>/docs/DECISIONS.md` |

- `[ ]` **같은 내용을 두 곳에 적지 않는다** — 반드시 어긋난다. 한쪽엔 본문, 다른 쪽엔 포인터만.
- `[ ]` 메모리(`memory/`)에는 **규칙 본문을 두지 않는다.** 한 줄 포인터 + 「왜/어떻게」만.
- `[ ]` **본문을 옮겼으면 가리키던 곳을 전부 고친다.** 절 번호 대신 **파일명 + 절 제목**으로 가리킨다.
- `[ ]` **「항상 먼저 읽어라」는 문서가 커지면 현재 상태와 이력을 가른다.**

### ⚠️ 문서를 지우는 것은 마지막 수단이다

**가끔 여는 문서는 지우지 않는다.** `PLAN.md`·`DECISIONS.md`·`TEACHER_GUIDE.md`처럼 **찾아 읽는
문서**는 자주 안 열려도 정상이다. **「안 읽는다」는 이유가 되지 않는다.**

지울 수 있는 것은 **네 조건을 모두** 만족할 때뿐이다.

- `[ ]` **같은 일을 하는 다른 문서가 이미 있다** (중복)
- `[ ]` **스스로 「계속 갱신한다」고 적어 놓고 실제로는 멈춰 있다** — 읽는 사람을 속인다
- `[ ]` **고유한 내용은 다른 문서로 옮겨 살렸다**
- `[ ]` **지우기 전에 사용자에게 무엇을 왜 지우는지 말하고 승낙을 받았다**

넷 중 하나라도 안 되면 **지우지 말고 고친다** — 머리말에 「여기까지가 최신」이라고 적거나,
지킬 수 없는 갱신 약속 문장을 지운다.

## 1. 결론을 미리 말해주지 않는다 ★

자료는 학생이 관찰해서 **스스로 찾아내는** 도구다. 안내 문구·라벨·주석은 **"무엇을 해 보라"까지만.**

"전류가 셀수록 자기장이 세진다" 같은 문장은 학생이 도달해야 할 결론이므로 화면에 적지 않는다.
코일에 N/S를 미리 붙이지 않는 것도 같은 이유다(자석 극처럼 **조건으로 주어지는 것**은 표시해도 된다).

## 2. 화면이 과학과 어긋나면 그래픽 결함이 아니라 틀린 것을 가르치는 것 ★

물리 법칙으로 방향·부호·크기가 정해지는 것을 그릴 때는 **검증 절차를 반드시 거친다.**

1. 이론값을 **코드를 쓰지 않고** 따로 구한다(오른손 법칙, F = I×B 등)
2. 모델과 대조하고 차이를 **수치(°·배율)로** 남긴다
3. **버그인지 오차인지** 판정 — 180°·90° 같은 딱 떨어지는 값은 버그다
4. 테스트에 **방향(손잡이)까지** 못 박는다 — "수직인가"류는 부호 뒤집힘을 통과시킨다
5. **일부러 버그를 되돌린 복제본에서 그 테스트가 실패하는지** 본다(변이 검사)
6. **렌더링까지** 확인 — 예측을 먼저 세우고 실제 화면과 대조한다
7. 화면에 **그려 놓은 조건**(전류 화살표, N/S, +/−)과도 맞는지 본다

> 2026-08-07에 직선 도선 나침반이 **180° 반대**를 가리키던 버그를 잡으며 만든 절차다.
> 그 버그는 기존 테스트를 **통과하고 있었다** — 검증이 약하면 없는 것과 같다.

전체 절차와 사례는 **`circuit/docs/물리_검증_절차.md`**(다른 프로젝트에서도 그대로 쓴다).

## 3. 화면 규칙

- **모바일 우선.** 탭 타깃 44px 이상, 가로 스크롤 금지. 학생은 대부분 폰으로 본다.
- **컬러 이모지 금지, 단색 아이콘 권장.** 이모지는 OS·폰트마다 모양이 달라 화면이 난잡해진다.
  아이콘에 색을 하드코딩하지 말고 글자색을 따라가게 둔다.
- **아이콘 단독으로 의미를 전달하지 않는다.** 상태는 **색 + 모양 + 글자** 세 겹으로.
  색만 쓰면 색약 사용자와 빔프로젝터에서 정보가 사라진다.
- **다크모드에서 안 보이는 색을 만들지 않는다.** 새 색은 **두 모드 모두에서 대비를 실측**한다.
  3:1 미만이면 사실상 안 보이는 것이다.
  - 실측은 **빌드 결과물**로(개발 서버는 변수 치환이 다르다). 측정 전에
    `*{transition:none !important}`를 주입한다 — 아니면 이전 색을 붙들어 가짜 값이 나온다.
  - 색은 계산된 값을 **캔버스에 찍어 RGB로 읽는다**. 요즘 CSS는 `oklch` 등으로 계산돼
    문자열에서 숫자만 뽑으면 엉뚱한 값이 나온다(21:1을 넘으면 파서가 틀린 것이다).

## 4. 한 UI를 여러 목적으로 공유할 때 ★

화면을 복제하지 않고 공유하는 것은 옳다(입력 폼이 두 벌이면 반드시 어긋난다).
문제는 **일부만 분기시키고 나머지를 잊는 것**이다.

- `[ ]` 목적에 따라 달라지는 것을 **전부 적어 놓고** 하나씩 지운다: 제목·안내문·**모든 입력칸의
  라벨과 placeholder**·입력 타입·버튼 문구·**제출 시 동작**·저장 위치·이동 주소.
- `[ ]` **분기 판단은 한 곳에만** 둔다. 순수 함수로 뽑아 양쪽이 같이 쓰고, 테스트로 고정한다.
- `[ ]` **목적마다 실제로 끝까지 눌러 본다.** 라벨만 읽으면 저장 위치가 틀린 건 안 보인다.
- `[ ]` 기존 옵션("저장 안 함" 등)이 **새로 추가한 값에도 걸리는지** 본다.

> 2026-08-08에 홈 패널을 두 목적이 공유하게 만들면서 첫 안내문과 버튼만 바꿨다. 라벨보다도
> **저장 위치가 틀려 그 경로로는 아예 못 들어갔는데 화면엔 아무 경고도 없었던 것**이 문제였다.

## 5. 수업자료 양식 변환은 "초안까지"다 ★

기존 수업 PPT의 **양식만 새 틀로 바꾸는 일**에서 내 몫은 **대강의 수정 초안**까지다.
마지막 다듬기는 선생님이 직접 하신다. 완벽하게 맞추려고 계속 붙들지 말 것.

- 내가 할 것: 일괄 변환(레이아웃·글꼴·색·번호 체계), 명백히 어긋난 것 정리,
  **바꾼 결과를 그림으로 보내 확인받기**
- 내가 안 할 것: 상자 하나하나의 폭·줄바꿈·미세 위치 맞추기. 몇 번 실패하면 **거기서 멈추고
  남은 것을 말로 보고**한다.
- 판단이 갈리는 지점(무엇이 제목인가, 이 원은 무엇을 가리키나)은 **초안 상태로 넘긴다.**

> 2026-08-15 지시: "앞으로 수업자료의 양식을 변경 적용할 때엔 대강의 수정 초안만 잡아주는
> 역할만 해. 나머진 내가 수정한다." 그날 완벽히 맞추려다 판별 규칙이 빗나가 **4개 파일을 손상**시켰다.

**기술적인 방법은 확장자별 절차서에** 있다 → `문서편집_라우팅.md`.

## 5-1. 문서를 고치거나 **읽기 전에** 갈래부터 나눈다 ★

**문서 파일(.hwpx·.pptx·.xlsx·.pdf·.bat·.ps1)을 고치거나 읽는 일이면
→ `문서편집_라우팅.md`를 먼저 연다.** 확장자마다 **읽을 절차서·주 도구·하지 말 것·검증 방법**이
표로 있다. 갈래를 안 나누고 시작해서 난 사고가 넷이다(그 문서 맨 아래).

⚠️ **`.pdf`는 고칠 일이 없어도 해당한다.** Read로 그냥 열면 쪽당 1,500~2,000토큰짜리 **이미지**가
들어온다. 텍스트가 든 PDF면 `pdf읽기.py`로 마크다운을 뽑아 **grep**하는 게 수십~수백 배 싸다
(292쪽 문서에서 한 줄 찾기: 약 55만 토큰 → 2천 토큰).

갈래는 셋: **① 무슨 파일인가 ② 무슨 목적인가(양식변환/내용수정/검증만) ③ 몇 개인가.**

### 자동화를 짤 때 — 웬만하면 에이전트 말고 워크플로

Anthropic 「Building effective agents」를 따른다(2026-08-23 채택).

- **워크플로**(경로를 미리 정함)가 기본. **에이전트**(AI가 스스로 판단)는 **열린 문제에만.**
  간단한 프롬프트로 되면 에이전트를 쓰지 않는다 — 성능을 얻는 대신 **지연과 비용**을 낸다.
- 만들 때는 **평가자-최적화자** 꼴로: 「만들고 → **기계로 검증하고** → 어긋나면 고친다」.
- **단순하게 유지 · 계획을 사람에게 보여줄 것 · 사람 감독 필수.** 5번 「초안까지만」과 같다.

## 6. 배포됐다고 말하기 전에 ★

GitHub Pages 배포는 **보통 1분 안팎**, 길면 10분.

⚠️ **문자열 하나만 grep해서 판단하지 말 것.** 2026-08-08에 찾은 문구가 **직전 배포에 이미 있던
값**이라 옛 파일에서도 걸렸고, 반영 전인데 "배포 완료"라고 보고했다. **반영 전인데 됐다고
말하는 건 안 된 것보다 나쁘다.**

- `[ ]` 배포 **전** 파일명(번들 해시)을 적어 두고 바뀌었는지 비교한다.
- `[ ]` 찾을 문자열이 **정말 이번에 처음 생긴 것인지** `git show HEAD`로 확인한다.
- `[ ]` 둘 다 맞으면 **실제 화면을 열어** 눈으로 한 번 더 본다.

## 8. 한글(.hwpx) 파일을 코드로 편집할 때 ★

학교 문서는 대부분 한글 파일이다. `.hwpx`는 **ZIP + XML**이라 코드로 고칠 수 있지만,
**함정이 전부 "조용히 실패"한다** — 오류도 안 나고 화면만 망가진다.

- **문단 몇 개면 한글에서 손으로 하는 게 낫다.** 코드는 **같은 구조를 수십 개에 반복**할 때만.
- **`<hp:linesegarray>`(줄바꿈 캐시)를 손으로 만들지 마라.** 글자가 겹쳐 뭉개지고
  **재저장으로도 안 고쳐진다.** 빼 두면 한글이 직접 계산한다.
- **스타일 ID는 파일마다 뜻이 다르다.** 쓰기 전에 **대상 파일의 `header.xml`에서 확인**할 것.
- **`cellSz height`는 최소 높이다.** 내용을 지워도 칸이 안 줄어 페이지 넘침을 오진하기 쉽다.
- **페이지 기하는 계산하되 임계값은 실측하라.** 계산값을 그대로 썼다가 33쪽이 55쪽이 됐다(임계 0.2mm).
- 검증은 **COM으로 실제로 열어** `PageCount`와 구조 개수를 대조. 화면은 PDF로 내보내 전달.

> 전체 절차·코드·사례는 **`hwpx_편집_절차.md`**. 2026-08-13~14 과학원 전시물 자료집
> (28개 전시물, 485MB)을 편집하며 만들었다.
