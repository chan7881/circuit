# 교육 자료 제작 공통 규칙

중학교 과학 수업에 쓸 자료를 만든다. 이 폴더 아래 프로젝트에서 작업할 때 함께 읽힌다.

**만드는 사람**: 중학교 과학 교사. 실제 수업에 쓰는 물건이고, 학생이 직접 만진다.

## 문서 지도 — 어디에 무엇을 적나

| 층 | 파일 | 담는 것 |
|---|---|---|
| 환경 | `~/.claude/CLAUDE.md` | 이 PC·원격 제어·파일 검색·브라우저 자동화 |
| **공통** | **이 파일** | 교육 자료를 만들 때 늘 지킬 것 |
| 프로젝트 | `<프로젝트>/CLAUDE.md` | 그 프로젝트의 구조·아키텍처·배포 절차 |
| 프로젝트 | `<프로젝트>/docs/` | 진행 상황·결정 기록·운영 정보 |

**새 규칙을 적을 때**: 다른 프로젝트에서도 통하면 여기, 한 프로젝트에만 통하면 그 프로젝트로. **같은 내용을 두 곳에 적지 않는다** — 반드시 어긋난다. 메모리(`memory/`)에는 규칙 본문을 두지 않고 한 줄 포인터만 남긴다.

## 1. 결론을 미리 말해주지 않는다 ★

자료는 학생이 관찰해서 **스스로 찾아내는** 도구다. 안내 문구·라벨·주석은 **"무엇을 해 보라"까지만** 쓴다.

"전류가 셀수록 자기장이 세진다" 같은 문장은 학생이 도달해야 할 결론이므로 화면에 적지 않는다. 코일에 N/S를 미리 붙이지 않는 것도 같은 이유다(자석 극처럼 **조건으로 주어지는 것**은 표시해도 된다).

## 2. 화면이 과학과 어긋나면 그래픽 결함이 아니라 틀린 것을 가르치는 것 ★

물리 법칙으로 방향·부호·크기가 정해지는 것을 그릴 때는 **검증 절차를 반드시 거친다.** 요약:

1. 이론값을 **코드를 쓰지 않고** 따로 구한다(오른손 법칙, F = I×B 등)
2. 모델과 대조하고 차이를 **수치(°·배율)로** 남긴다
3. **버그인지 오차인지** 판정한다 — 180°·90° 같은 딱 떨어지는 값은 버그다
4. 테스트에 **방향(손잡이)까지** 못 박는다 — "수직인가"류는 부호 뒤집힘을 통과시킨다
5. **일부러 버그를 되돌린 복제본에서 그 테스트가 실패하는지** 본다(변이 검사)
6. **렌더링까지** 확인한다 — 예측을 먼저 세우고 실제 화면과 대조한다
7. 화면에 **그려 놓은 조건**(전류 화살표, N/S, +/−)과도 맞는지 본다

> 2026-08-07에 직선 도선 나침반이 **180° 반대**를 가리키던 버그를 잡으며 만든 절차다. 그 버그는 기존 테스트를 **통과하고 있었다** — 검증이 약하면 없는 것과 같다.

전체 절차와 사례는 **`circuit/docs/물리_검증_절차.md`**에 있다(다른 프로젝트에서도 그대로 쓴다).

## 3. 화면 규칙

- **모바일 우선.** 탭 타깃 44px 이상, 가로 스크롤 금지. 학생은 대부분 폰으로 본다.
- **컬러 이모지 금지, 단색 아이콘 권장.** 이모지는 OS·폰트마다 모양이 달라 화면이 난잡해진다. 아이콘에 색을 하드코딩하지 말고 글자색을 따라가게 둔다.
- **아이콘 단독으로 의미를 전달하지 않는다.** 상태는 **색 + 모양 + 글자** 세 겹으로. 색만 쓰면 색약 사용자와 빔프로젝터에서 정보가 사라진다.
- **다크모드에서 안 보이는 색을 만들지 않는다.** 새 색을 넣었으면 **두 모드 모두에서 대비를 실측**한다. 3:1 미만이면 사실상 안 보이는 것이니 고친다.
  - 실측은 **빌드 결과물**로 한다(개발 서버는 변수 치환이 다르게 나온다). 측정 전에 `*{transition:none !important}`를 주입한다 — 아니면 이전 색을 붙들고 있어 가짜 값이 나온다.
  - 색을 잴 땐 계산된 값을 **캔버스에 찍어 RGB로 읽는다**. 요즘 CSS는 `oklch` 등으로 계산돼 문자열에서 숫자만 뽑으면 엉뚱한 값이 나온다(21:1을 넘는 비율이 나오면 파서가 틀린 것이다).

## 4. 한 UI를 여러 목적으로 공유할 때 ★

화면을 복제하지 않고 공유하는 것은 옳다(입력 폼이 두 벌이면 반드시 어긋난다). 문제는 **일부만 분기시키고 나머지를 잊는 것**이다.

- `[ ]` 목적에 따라 달라지는 것을 **전부 적어 놓고** 하나씩 지운다: 제목·안내문·**모든 입력칸의 라벨과 placeholder**·입력 타입·버튼 문구·**제출 시 동작**·저장 위치·이동 주소.
- `[ ]` **분기 판단은 한 곳에만** 둔다. 순수 함수로 뽑아 양쪽이 같이 쓰고, 그 함수를 테스트로 고정한다.
- `[ ]` **목적마다 실제로 끝까지 눌러 본다.** 라벨만 읽으면 저장 위치가 틀린 건 안 보인다.
- `[ ]` 기존 옵션("저장 안 함" 등)이 **새로 추가한 값에도 걸리는지** 본다.

> 2026-08-08에 홈 패널을 두 목적이 공유하게 만들면서 첫 안내문과 버튼만 바꿨다. 라벨이 틀린 것보다 **저장 위치가 틀려 그 경로로는 아예 못 들어갔는데 화면엔 아무 경고도 없었던 것**이 더 큰 문제였다.

## 5. 배포됐다고 말하기 전에 ★

두 프로젝트 모두 GitHub Pages로 배포된다. **보통 1분 안팎**, 길면 10분까지 걸린다.

⚠️ **문자열 하나만 grep해서 판단하지 말 것.** 2026-08-08에 찾은 문구가 **직전 배포에 이미 있던 값**이라 옛 파일에서도 걸렸고, 반영 전인데 "배포 완료"라고 보고했다. **반영 전인데 됐다고 말하는 건 안 된 것보다 나쁘다.**

- `[ ]` 배포 **전** 파일명(번들 해시)을 적어 두고, 바뀌었는지 비교한다.
- `[ ]` 찾을 문자열이 **정말 이번에 처음 생긴 것인지** `git show HEAD`로 확인한다.
- `[ ]` 둘 다 맞으면 **실제 화면을 열어** 눈으로 한 번 더 본다.

## 6. 커밋 전

- 테스트가 **전부** 통과하는지(실패 0)
- 바꾼 화면을 **실제로** 확인했는지
- 과학을 건드렸다면 2번 절차를 거쳤는지
- 임시 빌드·검증용 폴더가 커밋에 섞이지 않았는지
